# E4 rerun: enrichment deadline fix vs 2.0.3

Proof run for E4 (branch `e4-enrich-deadline`, fix commit `b530a1c`), the fix for R1 blockers B1 and B1a
(`docs/regression/2.1.0-vs-2.0.3.md` on `r1-regression`). Run 2026-10-17 with the R1 harness
(`benchmark/regression/` on `r1-regression`). Aggregate numbers only; raw runs are kept outside the repository.

| Criterion | Result |

### Why a stress replay as well

This window was much lighter than R1's:

- GitHub search was rate-limited for both versions, so the pages carried few CVEs: about 17 unique IOCs per run,
  against about 197 in R1.
- As a result, NVD did little in the matrix.

To test B1 itself, the stress replay took the pre-enrichment entity lists from 3 R1 runs in which 2.1.0 had
dropped the group:

| R1 query | Entities | CVEs |
|---|---|---|
| cve | 288 | 210 |
| malware_family | 309 | 205 |
| ransomware_group | 123 | 20 |

Each list was fed to the live enrichment phase of R1's 2.1.0 build and of E4, run one after the other (NVD rate
limits are per IP), over 2 rounds with the order alternated. A third round ran ransomware_group in reverse order.

**Per query, E4 vs the 2.0.3 rerun:**

- **E4 equal or ahead (7 queries):** actor_handle, crypto_wallet, long_query, generic_topic, no_results,
  onion_url (on relationships; behind on entities), malware_family (on relationships; behind on entities).
- **Mixed (1 query):** cve. One E4 run was well behind (22 entities, 11 relationships) and the other was level
  (119 entities, 156 relationships).
- **E4 behind (3 queries):**

  | Query | E4 (onion pages / entities) | 2.0.3 (onion pages / entities) |
  |---|---|---|
  | ransomware_group | 11 / 15–16 | 22 / 187 |
  | non_english | 9–11 / 4–8 | 15 / 11–92 |

  The third, brand_leak, was behind on relationships (0–2 against 9–130). Its MITRE (0 and 0, against 0 and 68)
  and entities (36–41, against 47–109) are at or just below the low end of 2.0.3's own spread between repeats,
  with the same number of pages (14–19 against 16–20).

- **Leaving out ransomware_group and non_english,** E4 is ahead on every metric (brand_leak is still included):

  | Metric (per run) | E4 | 2.0.3 |
  |---|---|---|
  | MITRE techniques | 57.1 | 47.9 |
  | Relationships | 173.6 | 125.7 |
  | Entities | 98.4 | 85.0 |

- **Spread between repeats is large in both versions.** For example, 2.0.3's MITRE count on generic_topic was 68
  in one run and 0 in the other.

**The shortfall in ransomware_group and non_english is not from the enrichment change:**

- R1 measured the same onion-page gap for 2.1.0 before E4: ransomware_group 11 onion pages, against 22–52 for
  2.0.3.
- Replaying the ransomware_group run's exact pre-enrichment entities through both versions' enrichment gives the
  same pages: no MITRE overlay in either, because those actor names do not map to an ATT&CK group.

## Notes (not changed by E4)

- **N-E4-1. 2.1.0 fetches fewer onion pages than 2.0.3 for some queries** (ransomware_group 11 vs 22–52,
  non_english 9–11 vs 15).
  - This was seen in R1 too, which attributed it to the intended onion quarantine.
  - It is the main cause of the remaining per-query gaps and deserves its own look; it is outside enrichment.
- **N-E4-2. ransomware.live returned HTTP 404 on `/groups` in every run of both versions, yet reads `ok`.** A 404
  is not counted as a failure by the request tracker. Same class as B1a, but in the HTTP-status layer.
- **N-E4-3. The entity-based MITRE overlay fires even when CVE entities are present.** It checks for the type
  `CVE`, but extracted CVEs are `CVE_NUMBER`. This is pre-existing and kept as is, so fast runs match the old
  output exactly.
- **N-E4-4. Two cases now read `error` where they used to read `ok`, because of honest statuses:**
  - `shodan_internetdb` reads `error` when every call it makes fails. That happened in both malware_family stress
    runs.
  - Sources that raise now read `error`.
- **N-E4-5. GitHub search was rate-limited in this window for both versions,** so these absolute numbers are
  lower than R1's and are not comparable with them. Compare the columns within this rerun.
